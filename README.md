# Учёт личных трат

Учебный проект: веб-приложение для учёта личных расходов студента. Серверный рендеринг на Go, без внешних веб-фреймворков.

## Стек

- Go, стандартный `net/http`
- `html/template` — серверный рендеринг HTML
- SQLite через `database/sql`, драйвер `modernc.org/sqlite` (чистый Go, без CGO)
- Material Design 3 — свой CSS, шрифт Roboto и иконки Material Symbols (Google Fonts)
- `golang.org/x/crypto/bcrypt` — хэширование паролей, сессии на cookie + таблица `sessions`
- `crypto/rand` + `crypto/hmac` — токены сессий и сброса, подпись CSRF-пары; отдельного секрета в конфиге нет
- Защита построена по OWASP Top 10, ASVS V2–V4 и Cheat Sheet Series — раздел «Защита» ниже

## Структура проекта

- *cmd/app* — **точка входа (main.go)**
- *internal/database* — **открытие SQLite и применение миграций**
- *internal/repository* — **ExpenseRepository, CategoryRepository, UserRepository, SessionRepository и ResetRepository, весь SQL-код**
- *internal/security* — **политика паролей, email, генерация и хэширование токенов, HMAC-подпись CSRF**
- *internal/handlers* — **HTTP-обработчики, middleware авторизации, лимитер попыток, заголовки безопасности и CSRF-проверка**
- *internal/models* — **структуры данных**
- *migrations* — **SQL-скрипты миграций**
- *web/template* — **HTML-шаблоны (layout, components, pages)**
- *web/static* — **CSS, JS**

## Запуск

Из корня проекта: **go run ./cmd/app**

При первом запуске создаётся файл базы **expenses.db** и применяются миграции из папки *migrations*. Применённые миграции записываются в таблицу `schema_migrations` и повторно не выполняются.

## Маршруты трат

Все они требуют авторизации: гость попадает на `GET /login`, а не на чужой список.

- `GET /expenses` — список трат и форма добавления; принимает фильтры `?category=2&from=2026-10-01&to=2026-10-31`
- `POST /expenses` — добавить трату
- `GET /expenses/{id}/edit`, `POST /expenses/{id}/edit` — редактирование
- `GET /expenses/{id}/delete`, `POST /expenses/{id}/delete` — удаление с подтверждением

## Маршруты авторизации

- `GET /register`, `POST /register` — создание аккаунта и вход сразу после регистрации
- `GET /login`, `POST /login` — вход; принимает `?next=/expenses?category=2` — адрес, на который возвращает после входа (только из allowlist, см. «Защита»)
- `POST /logout` — выход: сессия удаляется из базы, cookie снимается

## Маршруты аккаунта и сброса пароля

- `GET /account` — смена пароля (только для авторизованных)
- `POST /account/password` — смена пароля: текущий, новый, повтор
- `GET /forgot`, `POST /forgot` — заявка на сброс по email
- `GET /reset`, `POST /reset` — установка нового пароля по ссылке из письма

## Категории и фильтрация

- *categories* — таблица `(id, name)` с `UNIQUE` по названию; миграция `002_create_categories.sql` засевает базовые категории (Еда, Транспорт, Жильё, Развлечения, Здоровье, Прочее).
- *expenses.category_id* — **внешний ключ** на `categories(id)`. Целостность держится не только приложением: SQLite по умолчанию не проверяет `REFERENCES`, поэтому соединение открывается с `PRAGMA foreign_keys=ON` (`_pragma=foreign_keys(1)` в DSN) — трата с несуществующей категорией не вставится. Трата без категории — это `NULL`, а не 0.
- Список трат получает название категории **одним запросом** через `LEFT JOIN categories`: иначе на каждую строку таблицы ушёл бы отдельный запрос — это и есть проблема **N+1** (её и нужно избегать: один запрос вместо «1 + по запросу на строку»).
- Фильтры приходят **query-параметрами** (`r.URL.Query().Get("category")`), все они необязательные. `ExpenseRepository.List` собирает `WHERE` из только что заданных условий: список условий склеивается через `AND`, а значения уходят подготовленным запросом с `?` — фильтры не участвуют в склейке SQL строкой.
- Даты сравниваются напрямую с текстовым полем `date` (`YYYY-MM-DD`): в этом формате лексикографическое сравнение совпадает с хронологическим.
- Фильтр — обычная `GET`-форма, поэтому адрес можно скопировать или переслать, и он работает без JavaScript. Пустой или неразобранный параметр трактуется как «фильтр не задан» — битая ссылка отдаёт полный список, а не ошибку.

## Регистрация, вход и авторизация

- *users* — таблица `(id, email, password_hash)` с `UNIQUE` по email. Пароль в открытом виде в базе не появляется нигде: при регистрации `bcrypt.GenerateFromPassword` возвращает хэш со случайной солью (соль лежит внутри самой строки хэша), при входе `bcrypt.CompareHashAndPassword` сверяет введённый пароль с этим хэшем. Обратить хэш в пароль невозможно, а одинаковые пароли разных пользователей дают разные строки.
- *bcrypt не быстрыхэш*: стоимость 12 (`bcryptCost`) подобрана так, чтобы проверка занимала около 0.3 с — перебирать пароли офлайн становится дорого (Password Storage Cheat Sheet требует, чтобы стоимость была не ниже 10). Ограничение алгоритма — 72 байта входа, поэтому перед хэшированием пароль сворачивают в SHA-256 и base64 (`preHash`): длинная passphrase и полноценный Unicode-пароль работают целиком, а одинаково обрезанные префиксы не дают совпасть хэшам. Поля формы поэтому ограничены 256 символами, а не 72.
- *expenses.user_id* — **внешний ключ** на `users(id)`. Каждое обращение к тратам скоупится по владельцу: `List` добавляет `e.user_id = ?` первым условием, а `GetByID`, `Update` и `Delete` держат `id = ? AND user_id = ?`. Чужая трата при этом отдаёт 404, а не 403 — сервер не подтверждает, что запись с таким id существует.
- *sessions* — таблица `(id, user_id, expires_at)` с `ON DELETE CASCADE`: удалил пользователя — его сессии ушли вместе с ним. В базе лежит **sha256-хэш токена**, а сам токен живёт только в cookie: дамп базы не превращается в набор действующих сессий.
- *Почему таблица, а не карта в памяти*: map быстрее (нет запроса к базе) и не требует миграции, но живёт до перезапуска процесса и только в одном инстансе — после рестарта всех «разлогинит», а при втором сервере за балансировщиком сессия будет видна не везде. Таблица дороже на один `SELECT` за проверяемый запрос и разрастается, поэтому просроченные записи чистятся на старте (`SessionRepository.DeleteExpired`).
- *Cookie сессии* ставится через `http.SetCookie` с `HttpOnly` (js на странице не прочитает токен), `SameSite=Lax` (POST с чужого сайта cookie не получит — это базовая защита от CSRF, поверх которой лежит отдельный токен), `Path=/` и `Max-Age` по праздности сессии. `Secure` ставится только при TLS: на локальном http браузер такую cookie не отдаст вовсе.
- *Middleware авторизации* — `Auth.Required`: обёртка над обработчиком, которая доставает токен из cookie, находит сессию, и только затем вызывает `next`. Гостя она разворачивает на `/login` (`303 See Other`) до любой логики обработчика — проверять авторизацию внутри каждого хендлера не нужно. Для главной страницы есть `Auth.Optional`: она показывает и гостю контент, и авторизованному, но блокировать гостя не должна.
- *Передача пользователя в обработчик* — через `context.Context`: middleware кладёт `models.User` по ключу своего приватного типа (`userContextKey{}`), обработчик читает `currentUser(r)` из `r.Context()`. Ключ — тип, а не строка: строковый ключ мог бы совпасть с ключом другой библиотеки в том же контексте. Пользователь не принимается из поля формы или заголовка — только из сессии, иначе достаточно подставить `?user_id=2`.
- *Срок действия сессии* проверяется прямо в запросе: `WHERE s.id = ? AND s.expires_at > ?`. Если проверку убрать, токен становился бы бессрочным: украденная или оставшаяся на чужом компьютере cookie работала бы вечно, а «Выйти» перестал бы что-либо значить, потому что запись в базе осталась бы живой.
- *Выход* — `POST`, а не `GET`: ссылка-картинка на чужом сайте не должна разлогинивать пользователя. Он удаляет строку сессии и снимает cookie; оба действия нужны — cookie можно восстановить из истории, а сессию без удаления из базы можно было бы подставить вручную.
- *Ошибки входа* — одно сообщение на «нет такого email» и «неверный пароль»: страница входа не должна работать списком зарегистрированных адресов. Email нормализуется (`ToLower` + `TrimSpace`), иначе `A@b.ru` и `a@b.ru` разошлись бы по разным аккаунтам, хотя условие UNIQUE формально их различает.
- *Занятый email* определяется по коду нарушения `UNIQUE` от драйвера, а не предварительным `SELECT ... WHERE email = ?`: проверка отдельно от вставки оставила бы гонку, когда две одинаковые регистрации успевают пройти проверку одновременно.

## Защита

Раздел сделан сверх программы — по OWASP Top 10 (A01 Broken Access Control, A07 Identification and Authentication Failures), ASVS V2/V3/V4 и Cheat Sheet Series (Authentication, Session Management, Forgot Password, Password Storage). Логика вынесена в *internal/security* и *internal/handlers/limiter.go*, чтобы правила проверок не искали внутри HTTP- и SQL-кода.

### V2 — аутентификация

- *Политика паролей* — только длина (8–256 символов) и запрет известных: `CheckPassword` отклоняет пароль из стоп-списка утечек, пароль с пробелом на краю (легально «пароль » и «пароль» — разные строки, а пользователь об этом не знает) и пароль, совпадающий с email или его локальной частью. Подсказок про состав («добавьте цифру») нет специально: они диктуют злоумышленнику структуру и выдают правила фильтра.
- *Нет перечисления аккаунтов* — «Неверный email или пароль» одно на оба случая, а когда email не найден, пароль всё равно сверяется с `DummyHash` (валидным хэшем случайной строки). Без этой подставки ответ «нет такого аккаунта» приходит заметно быстрее, и по времени ответа строится список зарегистрированных адресов (WSTG-ATHN-04).
- *Перебор* — `Limiter` в памяти процесса: 5 неудач на аккаунт и 25 на адрес, окно 15 минут, блокировка 15 минут, ответ `429` с `Retry-After`. Пороги разные не случайно: выровняй порог на IP по порогу на аккаунт — и блокировка накатом била бы по всем клиентам NAT-провайдера. Заодно `Quota` ограничивает регистрацию с одного адреса, иначе бот налил бы мусор в `users` за минуту.
- *Смена пароля* (`POST /account/password`) требует текущий пароль — иначе украденная cookie мгновенно становится полным захватом аккаунта. После успешной смены удаляются **все** сессии пользователя и создаётся одна новая (ASVS V2.7.1, V3.2.1): старый украденный токен не переживает смену пароля. Эта форма под тем же лимитером, что и вход — иначе подбор текущего пароля шёл бы в обход блокировки входной страницы.
- *Сброс пароля* собран по Forgot Password Cheat Sheet: токен 256 бит из `crypto/rand`, в базе только его sha256-хэш, срок 15 минут, использование — один атомарный `UPDATE ... WHERE used_at IS NULL AND expires_at > ?` (две параллельные попытки по одной ссылке не пройдут обе), новая заявка гасит прежние, не больше трёх заявок на аккаунт за час. Ответ всегда «Если такой аккаунт существует, мы отправили ссылку»: страница `/forgot` не проверяет существование адреса. Слабый новый пароль ссылку не сжигает: токен гасится только после принятия валидного пароля.

### V3 — управление сессиями

- *Токен* — 32 байта `crypto/rand` (ASVS V3.1 требует минимум 64 бит энтропии и генератор, который нельзя воспроизвести): `math/rand`, «email + timestamp» или счётчик не подходят. В `sessions` лежит SHA-256 токена, сам токен уходит только в cookie.
- *Два срока вместо одного* — неактивность (`sessionIdleTTL` 12 часов) и предельный возраст (`sessionAbsoluteTTL` 7 суток). Оставить только неактивность — бессрочная сессия для того, кто держит вкладку открытой; оставить только предельный срок — пользователь теряет вход на середине работы. Продление скользящее, но с шагом (`sessionRenewalStep` 30 минут), иначе каждый запрос писал бы строку сессии в базе.
- *Ротация при входе* — сессия, выданная до входа, удаляется до выпуска нового токена (V3.2.2, защита от session fixation): подставленная заранее cookie не должна остаться действующей.
- *Флаги cookie* — `HttpOnly` (XSS не заберёт токен через `document.cookie`), `SameSite=Lax`, `Path=/`, `Max-Age` по сроку неактивности, `Secure` при TLS. `__Host-session` требует `Secure` и отказа от `Path`, поэтому включается тем же условием вместе с HTTPS.
- *Выход и очистка* — `POST /logout` удаляет строку сессии и снимает cookie (нужны оба: cookie восстанавливается из истории браузера, а живую строку в базе можно подставить вручную), `Auth.Cleanup` и `resetRepo.DeleteExpired` чистят мёртвые записи на старте.

### V4 — контроль доступа

- *Закрыто по умолчанию* — `Auth.Required` висит на всех маршрутах трат, `/account` и `POST /account/password`; гость уходит на `/login?next=...` до любой логики обработчика. Проверять «а авторизован ли вообще» внутри каждого хендлера не нужно — один middleware закрывает весь список.
- *Каждая операция ограничена владельцем* — `WHERE id = ? AND user_id = ?`, чужая трата отдаёт **404, а не 403** (V4.1.1): 403 подтверждает, что запись с таким id существует, и превращает перебор id в разведку. Это и есть защита от IDOR (WSTG-ATCT-BROKEN-01).
- *Приватные ответы с `Cache-Control: no-store`* — список трат и страница аккаунта не должны оставаться в кэше браузера или общей машины (WSTG-ATHN-03).
- *Возврат после входа* — `safeNext` принимает только `/`, `/expenses…` и `/account…` и отклоняет `//evil.example`, `http://evil.example`, `/\evil.example`, а также `\`, `@` и переводы строк. Наивная проверка «начинается с `/`» пропускает `//evil.example` — это адрес без протокола, браузер подставит текущий и уйдёт на чужой домен (WSTG-CLNT-04).
- *CSRF* — пара «cookie + скрытое поле формы», где в поле лежит HMAC от значения cookie (`Signer`), а не само значение. Проверка deny-by-default для всех `POST`/`PUT`/`PATCH`/`DELETE`, ответ 403 без подсказок. Это сильнее одного `SameSite=Lax`: Lax не спасает от cookie tossing с поддомена и от GET-эндпоинтов, которые что-то меняют.

### V5–V7 — закалка запроса и заголовки

- *Заголовки безопасности* навешивает `Security.Wrap` на весь маршрутизатор, то есть достаются и статика: CSP, `X-Content-Type-Options: nosniff`, `X-Frame-Options: DENY`, `frame-ancestors 'none'`, `Referrer-Policy: same-origin`, `Cross-Origin-Opener-Policy: same-origin`, `Permissions-Policy` с выключенными geolocation/микрофоном/камерой/платежами/USB, HSTS только при TLS (отправлять его с http — обещать то, чего нет).
- *CSP без `'unsafe-inline'`* — `script-src 'self'`, поэтому инлайновый скрипт темы вынесен в `/static/js/theme.js`. Политика перечисляет только то, что страница реально грузит (свои файлы и Google Fonts); при подключении Chart.js на этапе 6 CDN нужно будет дописать в `script-src`.
- *Размер тела* — `MaxBytesReader` плюс `413` по одному только заголовку `Content-Length > 1 MiB`: запрос отклоняется до вычитывания, поэтому «заголовок на гигабайт, тело по каплям» не держит соединение и память (V5.1).
- *Таймауты сервера* — `ReadHeaderTimeout` 5 с, `Read`/`Write` 20 с, `Idle` 60 с, `MaxHeaderBytes` 64 KiB. Без `ReadHeaderTimeout` медленный клиент (slowloris) занимает goroutine бесконечно.
- *Инъекции и XSS* — вывод идёт через `html/template` (экранируются и хранимые описания трат, и отражённые значения из query), весь SQL — подготовленные запросы с `?`, payload вроде `' OR 1=1 --` остаётся данными. `clientIP` намеренно не верит `X-Forwarded-For`: любой клиент мог бы подставить этот заголовок и обойти блокировку.
- *Обработка ошибок* — `404`/`400` без внутренних деталей, стек и текст ошибки шаблона уходят в лог, а не в ответ (WSTG-ERR-HNDL). Запрос вида `GET /static/../expenses.db` файл не отдаёт: `http.FileServer` чистит путь от `..`, а база лежит вне doc-root (`web/static`).

### Почему не JWT

Cheat Sheet по JWT не запрещает его, но в этом приложении расход на него выше, чем польза: подпись и проверка обязательны (алгоритм нельзя брать из заголовка, `alg=none` недопустим), токен в cookie всё равно требует CSRF-защиты, а в `localStorage` — читается любым XSS. Главная потеря — отзыв: stateless-токен живёт до истечения срока, поэтому «Выйти», смена пароля и блокировка перестают действовать мгновенно. Возвращать отзыв можно либо коротким TTL с refresh-механизмом, либо реестром сессий на сервере — то есть тем же поведением, которое здесь уже даёт таблица `sessions`. Выгоды stateless в этом проекте нет: API нет, инстанс один, балансировщика нет, поэтому серверные сессии и оставлены (ASVS V3.2 выбирает их, когда нужен немедленный отзыв).

### Как это проверено

Проверка — прогоны по WSTG против запущенного сервера, а не чтение кода: 34 проверки авторизации этапа 5 и 94 проверки защиты (политика паролей, перечисление и время ответа, блокировка перебора, флаги cookie, ротация и отзыв сессий, все варианты CSRF — отсутствие поля, поддельная подпись, кросс-сайтовый запрос, cookie tossing, плюс позитивный контроль; заголовки, 413 и таймауты, open redirect, хранимые и отражённые XSS, SQL-payload, утечка информации через 404, смена и сброс пароля, доступ к чужим объектам). Проверочные скрипты в репозиторий не внесены: они работают с локальным `expenses.db` и `server.log` и содержат пути конкретной машины.

## Дополнительно (сверх программы)

- Переключение светлой и тёмной темы (кнопка в шапке): палитры Material Design 3, выбор запоминается в `localStorage`, по умолчанию берётся системная тема.
- Анимации в духе Material: ripple-волна из точки нажатия на кнопках и навигации, микро-взаимодействия иконок (поворот, сдвиг стрелки), press-эффекты; при `prefers-reduced-motion` вся декоративная анимация выключается.
- Анимации операций с тратами: при добавлении/сохранении текст кнопки «растворяется» по буквам, взрывается конфетти и появляется галочка «Готово»; новая строка влетает в список с подсветкой, отредактированная — мягко мигает; удаление подтверждается удержанием кнопки (hold-to-delete с заливкой), строка вылетает, а соседние плавно сдвигаются (FLIP). Без JavaScript и при `prefers-reduced-motion` все операции работают обычными формами.
- Защита по OWASP — политика паролей и bcrypt с пре-хэшем, блокировка перебора, серверные сессии с двумя сроками и ротацией, CSRF-пара с HMAC-подписью, смена и сброс пароля, заголовки безопасности, лимит тела и таймауты, allowlist возврата после входа. Всё разобрано в разделе «Защита», проверено прогонами по WSTG.
- Фирменный курсор-рука вместо системного (только на сайте): движется за указателем на пружине с перелётом, наклоняется по ходу движения и слегка доворачивается при торможении, чуть увеличивается над кликабельными элементами и сжимается при нажатии. На тач-устройствах, без JavaScript и при `prefers-reduced-motion` остаётся обычный системный курсор.

## Известные ограничения текущей версии

- Суммы хранятся в копейках (`int64`), в форме вводятся в рублях с копейками (`250.50` или `250,50`)
- Категории — фиксированный справочник из миграции: своих категорий у пользователя пока нет, и нет админки для их переименования
- Иконки Material Symbols подключаются подсписком (`icon_names=` в ссылке на Google Fonts в `web/template/layout/base.html`): новый значок надо дописать в этот список, иначе вместо иконки браузер показывает текст `filter_alt`
- Фильтр по датам не проверяет, что «от» раньше «до»: при перевёрнутом диапазоне список просто окажется пустым
- Путь к базе и порт пока заданы в коде — вынос в `.env` на этапе 8
- При неверных данных **формы траты** сервер возвращает 400 без повторного показа формы — будет доработано на этапе 7; формы входа и регистрации уже показывают причину ошибки
- Валидация форм трат пока минимальна (обязательные поля, сумма и дата): подсказки по каждому полю и возврат введённых значений — этап 7. Пароли и email проверяются строже, см. «Защита»
- Траты, добавленные до этапа 5, остались с `user_id = NULL` и никому не показываются: в новой базе таких записей нет
- Чистка просроченных сессий и токенов сброса выполняется на старте сервера (`Auth.Cleanup` и `resetRepo.DeleteExpired`); долгоживущий процесс без рестарта копит мёртвые строки в таблицах `sessions` и `password_resets`
- Счётчики попыток (`Limiter`) живут в памяти процесса, а секрет HMAC для CSRF выдаётся при старте: отсюда ограничение на один инстанс (за балансировщиком лимиты не сойдутся), а после рестарта все открытые до него формы отдадут 403 до перезагрузки страницы
- `Secure` у cookie и HSTS включаются только при TLS: локальный запуск — это http, а с `Secure` браузер не отдаст cookie вовсе. HTTPS, второй фактор (MFA), подтверждение email при регистрации и удаление аккаунта не сделаны
- Ссылка сброса пишется в серверный лог (`logMailer`): SMTP нет, поэтому «письмо» видит только тот, у кого есть доступ к логу. Интерфейс `Mailer` подставит настоящего отправителя, не трогая обработчики
- Пароли users заведены с пре-хэшем SHA-256, поэтому перенос готовой таблицы с «чистыми» bcrypt-хэшами потребует их пересчёта: в этой базе таких записей никогда не было (миграция `003_create_users.sql` появилась уже с пре-хэшем)
- Квота регистрации считается по IP: за общим NAT (провайдер, кампус) лимит в 30 заявок на 15 минут делится на всех его клиентов
